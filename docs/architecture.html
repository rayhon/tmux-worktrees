dev infrastructure · pooled worktrees

treehouse×herdr — one command per branch, a full stack per worktree

Claude CLI runs the tmux-worktrees skill to lease a worktree from a treehouse pool off your clone, put it on a branch, and launch its dev stack. herdr — one local server — renders every worktree as a labeled tab of panes. How many panes, which services, which ports, what layout: all read from one tmux-worktree.yaml; no project values live in the scripts.

why it's good

Working several branches at once usually means cloning the repo three times, fighting port collisions, waiting on npm install, and killing dev servers you didn't mean to. This skill collapses all of that into one command per branch — and a live, labeled view of every stack at once.

01

Real stacks, in parallel

Each branch gets its whole dev stack running — not just a checkout. Review, test, and demo several features live at the same time.

02

Warm pool, no cold start

Slots are reused — node_modules, env and ports stay warm. A lease is instant; no per-branch install tax.

03

Your real data, isolated

Worktrees share your clone's .git + R2 blobs (real data) but keep per-slot sqlite — no empty test DB, no cross-branch corruption.

04

One command, one view

wt-up <branch> → a herdr tab. No manual tmux wiring, no port juggling, and return never kills your session.

The three pieces

// what each one does, and why

Two concerns, kept separate. treehouse owns the worktrees (creating, leasing, returning them). A multiplexer owns the view — many live dev-server panes on one screen so you can watch a whole stack at a glance. tmux is the classic multiplexer; herdr is the agent-native upgrade. The skill lets you use either.

Pool manager

treehouse

Manages the worktrees. Keeps a small pool of reusable git worktrees off your clone. get --lease hands you a warm one, a post_create hook wires its ports / env / R2 mirror, return frees it for the next task.

Why: no cloning or npm install per branch; branches stay isolated but share your real data.

The view · recommended

herdr agent-native

Shows the worktrees. One persistent local server, sessions saved to disk, a tab per worktree that carries the branch name and live pane status. Attach any time to watch every stack.

Why over tmux: survives restarts, shows branch + agent status, and is built for driving CLI agents.

The view · classic

tmux also supported

The original multiplexer the skill launched on — still fully supported from the same yaml. Reach for it if you already live in tmux; otherwise herdr gives a richer, restart-proof view.

Why keep it: zero new tooling — one config drives both, so the choice is yours per machine.

◇ THE GLUE The tmux-worktrees skill (run by Claude Code) ties them together: it reads your tmux-worktree.yaml, asks treehouse for a slot, and launches the panes in tmux or herdr. No project values live in the scripts.

One yaml drives it all

// tmux-worktree.yaml · repo root

This file is the whole configuration. It names the main pane, lists the service panes with their ports and commands, and sets the layout. The same file feeds both the tmux and herdr launchers — change it once, both follow.

tmux-worktree.yaml
Amain:
    label: CLAUDE       # the agent pane
    cmd: claude

Blayout:
    main_ratio: 0.70    # 70% width to CLAUDE
    zoom_main: false

Cservices:
  - label: MCP
    cwd: apps/mcp/mcp-hub   D
    port: 8787              E
    cmd: npx wrangler dev --port {PORT}
  - label: WEB
    cwd: apps/web
    port: 3000
    env: {MCP_URL: "{MCP_URL}"}   G
  - label: AGENT
    cwd: apps/agentic/agent-hub
    port: 51957

# shared ONCE at the root — not per service:  F
symlinks: [src/data]           # plain symlink
mirror_with_sqlite_copies:        # hybrid R2
  - .wrangler/state              # blobs symlinked, sqlite copied
A

main — the agent pane

The wide pane that runs claude. One per worktree; everything else is a service.

B

layout — the split

main_ratio 0.70 gives CLAUDE 70% of the width; services share the rest. zoom_main optionally full-screens it.

C

services[] — the pane count

N services → N+1 panes. This list is exactly why a repo gets 2, 4, or 6 panes — nothing is hardcoded.

D

cwd — where it runs

Path (relative to the worktree) the pane starts in, e.g. apps/web.

E

port — the base

Base port; the pool adds a per-slot offset (+110/+120…) so worktrees never collide.

F

symlinks / mirror_with_sqlite_copies — shared state

Declared once at the root, applied to every service. symlinks = plain symlink for static dirs; the hybrid mirror is for .wrangler/R2 — blobs symlinked (real data), sqlite copied per-slot so wrangler dev runs in parallel. Read by link-worktree-env.sh, not the launcher.

G

{LABEL_URL} — cross-links

Templates like {MCP_URL} resolve to the sibling's localhost:<port> — panes reach each other.

How a worktree is created

// what wt-up.sh runs, and why — the herdr + treehouse flow

One command fans out to several scripts. Green chips are the skill's own scripts; amber is the external treehouse binary; cyan is the herdr launcher. Steps 3–4 are fired by treehouse as its post_create hook. The scripts hold no project values — your project is described only in tmux-worktree.yaml, which two steps read: link-worktree-env.sh (ports & the shared paths to symlink) and herdr-worktrees.sh (the panes / layout).

wt-up.sh <branch>your script · entry

Orchestrator. The one command you (or Claude) run. Drives every step below, then prints the attach line.

treehouse get --leaseexternal binary

Makes/leases the git worktree. Hands back a free pooled slot under ~/.treehouse/… — reused if warm, created if the pool needs to grow.

th-postcreate.shyour script↳ fired by treehouse post_create

Seeds the port offset. Derives a pool-unique offset from the slot number (100 + slot×10) so this worktree's ports never collide with others, then calls…

link-worktree-env.shyour script↳ reads tmux-worktree.yaml

Wires the worktree — from the yaml. Reads the ports and shared paths you declared: each service's port, the top-level symlinks: list, and an optional hybrid-mirror list for stateful dirs. Then it applies the pool's port offset, copies each service's local env files, symlinks the paths you named so the worktree reuses the parent's real data, and kicks off the dependency install. The script is project-agnostic — what to share and on which ports is your yaml's call, not the script's.

wt-up.shyour script · cont.

Branch + session. Checks out <branch>, clears the reused slot's stale Claude history and restores that branch's saved session (or starts fresh), and installs the post-checkout/post-rewrite label hook.

herdr-worktrees.shyour script↳ reads tmux-worktree.yaml

Builds the view — the yaml's other half. Reads $REPO/tmux-worktree.yaml with yq to learn your project's shape: the herdr layout (main ratio, zoom), and for each service which app to bring up, in which dir, on which port, with which start command. Then it ensures the herdr server (from $HOME), splits the panes per that layout, launches each service's command, and labels the tab with the branch. The launcher is generic — every app and port comes from your yaml, not the script. (The tmux path's tmux-worktrees.sh reads the same file.)

herdr-relabel.shyour script↳ git hook, later

Keeps the label honest. Runs on every later git checkout/rebase in the worktree so the tab always shows the current branch (or free-<slot> when released).

Worktree = branch

An active slot is checked out on a branch; its tab shows that branch. Released → detached HEAD → tab reads free-<slot>.

Per-branch session

Each CLAUDE pane links to a branch-keyed Claude session .jsonl — restored on return, fresh on a new branch. No leaked context.

Ports don't clash

Every slot gets offset +110/+120/+130…, so all worktrees' mcp-hub · web · agent-hub run at once, side by side.

Return is safe

wt-down.sh saves context, detaches the branch, returns the slot to the pool — herdr stays up, the tab relabels to free.
